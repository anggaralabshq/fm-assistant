## Q1: the mechanism

`SI.Bindable.Bindings.GetHandler(TypedValue source, Property property, List<string> outRequiredContext)`
returns the data handler for a property and the names of the **binding contexts** it needs. The binding system
looks a context up by node name, walking up from the property node (a panel provides them as variables, e.g. the
portal has nodes `Team`, `stringtype`, `PortalMessagesTab`). A plain planted root has none of them, so the channel
never opens: that is why these props were `_missing` headless, and why planting under the `Human` node alone did
not help (it supplies `human` but not `team`).

Fix (ops only, `Reader.PlantOne(..., ctx)`): plant `__fm_N` (no value) with one child per context
(`__fm_N.team = TeamReference`, `__fm_N.human = PersonReference`, …) and the parent at `__fm_N.subj`; bind the props
under `subj` as before. Close removes `subj` then the wrapper. `NodeFlags` were not the issue
(`None`/`Temporary`/`RequiresContext`/`Default` only; no context setter exists on `Bindings`).

Discovery tools (dev only): `ctx_probe` (handler + required contexts per name, no channel opened),
`tree_probe` (which value types in the live tree have a handler for given names), `read` now takes
`ctx: {name: {ref|path|int|bool|string}}`, `each` (plant every element of a list prop), `ref: persons` with
`uids[]` (bulk), and `probe` (GetHandler on every landed value).

### Star ratings: masking (most important)

- Scale: an int on a 0–20 scale, not raw ability. The squad screen's star widget (`FM.UI.FMStarRatingTemp`,
  bindings `starrating.minvalue` / `starrating.maxvalue`) received exactly the values the headless read gave for
  the same players (unmapped `18-18`, `15-15`, `17-17`, `14-14`/`14-15`) and mapped them to `8`, `5`, `7`, `4` (half-star units, inferred from
  `GetFullAndHalfValues`): **stars = (value − 10) / 2** for these (non-youth) players. Values below 10 and the youth
  configuration (`FMStarRatingSettings.YouthConfig`) were not seen; verify before relying on the formula there.
- Knowledge masking is applied by the game: unknown players read `MinValue = MaxValue = −1` (494 of 500 search
  rows, knowledge level 0); partly scouted players (knowledge 2/5) read ranges such as `13-14`, `13-16`; own
  players read `n-n`, and a loanee-in read CA `16-16`, PA `18-20` (a range even for an own player).
- No raw ability number was returned by any star prop (all values ≤ 20 or −1). `IsScoutsOpinion` was `False` in
  every person-level read; inside `ClubCoachReport.ScoutedCurrentAbilityInfo.StarRange` it is `True`.
- Masking depends on the `team` context = the viewer's team. Always plant `Human.Team`; never another team.

### Risks found

- **`Morale` for players the manager cannot view returns numbers too** (negative, −10…−15, varying by player) for
  other clubs' players, where `CanViewHappinessInfo` is `False`. Treat it as not visible: gate every
  morale/happiness read on `CanViewHappinessInfo == "True"` and drop the value otherwise.
- `Boolean` (tactic) and `StringType` (portal search text, presumably) meanings are inferred, not confirmed.
- Context names are per property and come from the game; a production op should ask `GetHandler` (or a fixed
  per-prop table checked at startup) rather than assume, so a renamed context fails loudly (`binding-api-changed`).

Timings (round trip, game idle): one person, 6 context props, all landed: 1.19 s (was 4.2 s with the same props
`_missing`). 500 persons × 4 context props in one plant batch: 561 ms in game, 1.6 s round trip. Tactic + chain:
1.4 s. Happiness block (13 props): 1.25 s.

## Q2: inbox list

**Solved without any screen.** `read {ref: path, path: "Human", props: ["HumanPortalFilteredMessages"],
ctx: {team: Human.Team, StringType: "", PortalMessagesTab: 0}}` returns the list of `FM.UI.NewsItemReference`
values, newest first; planting each element directly (`each`) gives the phase 1c per-item props headless
(`Date`, `NewsItemTimeSent`, `NewsItemId`, `NewsItemHasBeenRead`, `MediaNewsCategory`, `NewsItemAction`,
`NewsItemIsImportant`, title/body as in phase 1c).

- `PortalMessagesTab`: 0 = all (75 items here, ~3 weeks, same span as the rendered list), 1 = new (5), 2 = tasks
  (0), 3 = unread (0). Same numbers with the portal closed.
- `NumberUnreadMessages` (ctx `team`) → 0 here.
- Timing: list + 75 items × 7 props: 1.47 s round trip (items: 260 ms in game).
- "Since a date": filter on `Date` (+ `NewsItemTimeSent`); the list is date-descending, so stop at the first item
  older than the cut-off. Items older than the portal's window are not in the list.
- `NewsItemReference` by id is **not** a valid alternative: `NewsItemId` is not monotonic (consecutive items read
  e.g. 448, 220, 198, 574, 73), so counting ids down from the newest does not walk the inbox. Not pursued.
- Extending `ListRead` to `VirtualisedList` / `StreamedObjectList` is not needed for the inbox.
- `HumanIncomingMessages` (ctx `Date` = today) returned `[]`; its semantics (messages of a given day?) unverified.

## Q3: profile route

**Opening: solved.** The game's own person-link handler
(`FM.UI.EmbeddedDataHandler.m_personReferenceClickedHandler`, a `PersonReferenceClickedHandler` on the
`EmbeddedDataHandler` ScriptableObject, found with `Resources.FindObjectsOfTypeAll`) holds the profile panel
references and parameter names:

| field | value |
|---|---|
| `m_playerPanelRef` / `m_playerParamName` | PanelID GUID `77188c7bbd58fe54f9aa75e6d2c9a146` / `player` (opens panel `PlayerReport`) |
| `m_nonPlayerPanelRef` / `m_nonPlayerParamName` | `0ae42127e374d4a42acdcc948831ba15` / `person` (opens `NonPlayerReport`) |
| `m_teamParamName`, `m_nprTeamParamName`, `m_compParamName` | `team`, `team`, `comp` |
| `m_teamContextName` | `reportcontextteam` |
| agent / retired / human / in-match profile panels | `22ae184e…`, `f1505363…`, `91b6526e…`, `89af37ab…` (not opened) |

`PanelManager.Open(AssetReferenceT<PanelID>(guid), paramName, PersonReference(uid), null, null,
RebindMethod.None)` opens the profile in ~1.1–1.3 s, with data context (unlike opening a GUID without a
parameter): the panel root `<guid><counter>` holds `Player`/`Team`, and the game's navigation sets
`gameworldsubtabsandbookmarks.CurrentViewedPlayer` and builds `PlayerEntitySubtabs` (dev op `profile_open`, run
under `UiLock` and only on the normal game screens). Read the GUIDs and param names from the handler at runtime
rather than hard-coding them. The profile's sub-tabs include contract-offer tabs (nodes carrying
`ContractOfferScreenValidation`); a production route must never select those.

**Demands: blocked.** With a player profile and a free-agent staff profile open, `tree_probe` over the whole
binding tree (59 / 57 value types) found no type with a handler for any `Estimated*` name or
`IsWillingToEnterNegotiations` / `UnwillingToEnterNegotiationsDescription` / `DisplayedDemandsDescription`. The
profile overview binds none of them either. Conclusion: they belong to the contract-offer / negotiation flow
(types such as `ContractEditSessionReference`), which this spike must not open. Readable non-negotiation
substitutes:

- `Person.ClubCoachReport` (ctx `human`) → `PlayerReportReference` → `ScoutedTransferInfo` =
  `{ExpectedTransferValue, ExpectedWageDemands, ExpectedTransferInterest, ExpectedLoanInterest}`, each
  `{ShortString, LongString (localized), ProConRating: int, IsPro: int}`. In this save no player has a scout
  report (`HasScoutedInfo` `False`, wage `"T/A"`), so a populated value was not seen.
- `Person.ScoutedMinWage` / `ScoutedMaxWage` (ctx `team`, `human`): `{display, sort}`; all unscouted here.
- `PlayerAgentDemands` (phase 1c) for agent-initiated demands.

Not read on purpose: `ContractEditSession`, `ContractOfferScreenValidation`, `CanBeOfferedContract` (they exist on
a person; an edit session is a negotiation object).

## Recommended Phase 1d scope

1. Production `ReadScope` contexts: keep `Reader.PlantOne(..., ctx)`; add a startup check that the expected
   context names per prop still match `GetHandler` (fail as `binding-api-changed`).
2. `inbox` op (F1): `HumanPortalFilteredMessages` (tab 0) + per-item props, `since` filter, unread count;
   no screen needed.
3. Morale / happiness in `form` / `squad` (F2), gated on `CanViewHappinessInfo`.
4. Star ratings (`CurrentAbilityStarRange`, `PotentialAbilityStarRange`) in `squad`, `players search` and
   `loans`, as `{min, max}` half-star counts, `null` when −1; verify the youth mapping first.
5. Active tactic headless (F3) from `Team.Tactic` (ctx `Boolean`), replacing the SquadScreen route.
6. `HasTeamReport` (F8) via ctx `TeamRequestingReport`.
7. Profile route kept as a dev/nav building block only; wage demands stay Phase 2 (negotiation), with
   `ClubCoachReport.ScoutedTransferInfo.ExpectedWageDemands` as the read-only estimate when a scout report exists.
