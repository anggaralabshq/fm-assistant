## Method notes (read first)

- **Property-name harvesting.** `fm.app/Contents/Resources/Data/il2cpp_data/Metadata/global-metadata.dat`
  holds every binding property name as concatenated, alphabetically sorted string literals. Splitting
  around a keyword at CamelCase humps (spans of 1–7 humps) and sending the candidates (hundreds to a few
  thousand per call) to `prop_check` gives the names that exist in this build in about 1 s. This is how
  every name below was found; it replaces guessing.
- **Headless vs. context-bound props.** `read` plants children under a fresh root node
  (`NodeFlags.RequiresContext`, no panel context). Many props resolve that way (all "headless" below).
  A second class exists in `prop_check` but never lands headless, even with `wait_ms` 12000, even when the
  parent is the very same reference a panel uses (tested with the portal's own `Human` node and the squad
  screen's own `TeamReference`): `Team.Tactic`, all `Human*` inbox/news lists, `NumberUnreadMessages`,
  `Morale`, `Happiness*` (per player), star ratings, `EstimatedWageDemands`, `IsWillingToEnterNegotiations`,
  `HasTeamReport`. Hypothesis: they need the binding context a panel provides (the viewer). They can still
  be read through `read {ref: "path"}` when a panel already holds the value as a node (props *of* that
  node's value then land, see F3). A plugin change that plants under a panel's context (or sets a context
  on the planted root) may make them headless; not tested (would need a plugin change).
- **Panel node names are not stable.** The tree root holds one node per open panel, named
  `<PanelId><hex counter>` (e.g. `SquadScreen42`, then `SquadScreen44` after re-opening) or
  `<PanelID GUID><hex counter>` (the portal: `2d1049f4571df444eb050b39a5b8aaec` + counter; tactics:
  `a69d2d19d0ea8054b82d191ecfea01be` + counter). Sub-paths below them are numeric/generated too. An op must
  find the node by walking the tree for a value of the right type (e.g. first `TeamTacticReference` child
  named `Tactic`), not by a fixed path.
- **Read timing.** `read` returns in ~1.0–1.3 s when every requested prop lands, and in about
  `wait_ms` + 0.2–1 s when any prop is missing (it waits for the missing ones). `tree`, `prop_check`,
  `ui_dump`: ~1.0 s. `nav_open {tab}`: ~3.5 s; `nav_open {panel: SquadScreen}`: ~1.4 s;
  `nav_open {panel: PlayerSearchReport}`: ~2.2 s. Production ops should request only props known to land.
- **Hidden values.** Names such as `PlayerPotentialAbility`, `PotentialAbilityScore`,
  `PerceivedPotentialAbility` (int, read once by accident while probing loans) and `DebugHappinessScore`
  exist and some resolve headless. They are not what the manager sees; spec §6 forbids using them. Do not
  request them.
